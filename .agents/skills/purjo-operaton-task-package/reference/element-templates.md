# Element templates

Generated by the `operaton-contracts` package from the `TaskTemplate` specs in
`OperatonTasks.py` and the `TaskContract` models in that module. Configure it
in `pyproject.toml`:

```toml
[tool.operaton-contracts]
specs = "OperatonTasks:TEMPLATES"
icon = "{{package}}-logo.svg"
reserved-topics = []
```

When `OperatonContracts` is already a runtime dependency, co-locating the
specs in `OperatonTasks.py` adds no package dependency. To keep template
metadata build-time-only, put it in a root-level `OperatonTemplates.py`,
configure `specs = "OperatonTemplates:TEMPLATES"`, and list that module in
`.wrapignore`. Keep the icon at the project root and list it there too.

```console
make element-templates          # python -m OperatonContracts generate
make test                       # … check (drift + consistency, offline)
make check-element-templates    # … validate (pinned upstream schema, network)
```

In `OperatonTasks.py`, declare `TEMPLATES` after the task models. A separate
module imports the contract classes from `OperatonTasks.py` instead.

## Spec

```python
from OperatonContracts.templates import ElementType, TaskTemplate, TemplateGroup

TaskTemplate(
    topic="sisu.generic.study_rights.rescind",
    template_id="fi.sisu.purjo.study-rights-rescind",   # stable; never reuse
    name="Sisu: Rescind Study Rights",
    description="Rescind active study rights in Sisu.",
    filename="sisu-study-rights-rescind.json",
    inputs=RescindStudyRightsInput,
    outputs=WriteResultOutput,
    groups=(TemplateGroup("sisu", "Sisu"),),  # default: inputs/Inputs, outputs/Results
    input_group="sisu",            # group id for inputs (default "inputs")
    output_group="sisu",           # group id for outputs (default "outputs")
    version=1,                     # bump when a published template changes
    icon="sisu.svg",               # optional; replaces the configured icon
    keep_versions=(),              # earlier published versions kept in the file
    element_type=ElementType.SERVICE_TASK,  # or SEND_TASK, BUSINESS_RULE_TASK,
                                   # MESSAGE_INTERMEDIATE_THROW_EVENT, MESSAGE_END_EVENT
)
```

`input_group` and `output_group` must be ids in `groups`; use one id for both
to show every property in a single panel group.

After a template is published, bump `version` for every change and add the
previous version to `keep_versions`: `generate` copies kept versions unchanged
from the committed file (a JSON list, newest first), so the modeler can still
upgrade diagrams using them. The worker serves only the latest contract.
Commit `.operaton/` when using `keep_versions`; remove a version by dropping
it from the tuple and running `generate`.

The CLI reads the package configuration and uses the pinned schema by default;
set `schema-url` when the package must pin a different schema version.

## Generated structure

`$schema, name, id, description, version, appliesTo, [elementType,]
groups, properties, icon`. `appliesTo` is the `element_type`'s BPMN type;
message events (`MESSAGE_INTERMEDIATE_THROW_EVENT`, `MESSAGE_END_EVENT`) add
`elementType: {value, eventDefinition: "bpmn:MessageEventDefinition"}`, and
their `camunda:type`/`camunda:topic` land on the message event definition.
`MESSAGE_END_EVENT` needs an outputs contract without fields: the engine
rejects output mappings on end events.
Properties start with Hidden `camunda:type = external` and
`camunda:topic = <topic>`.

## Input mapping (`model_json_schema(by_alias=True)`)

| JSON Schema | Template property |
|---|---|
| `boolean` | `Boolean` |
| `string` (incl. `format: date`) | `String` |
| `string` + `enum` (`Literal`) | `Dropdown` + `choices` |
| `array` of `string` | `List` + `itemType: "String"` |
| `array` of `string` + `items.enum` | `List` + `choices` + `display: "taglist"` |
| `object` of `string` (`dict[str, str]`) | `Map` + `entries` (hint, `Literal`, or `Enum` keys), else `additionalEntries: true` |
| anything else | error unless `template_hints(type=...)` |

- `value`: `template_hints(value=...)` → schema `default` → `[]` for `List`
  → `"${alias}"`. The value must fit the type (`str` for String, Text,
  Hidden, Dropdown; `bool` for Boolean; `list` for List) or rendering fails.
- `type` hints must be one of String, Text, Hidden, Dropdown, Boolean, List,
  Map; a Dropdown needs `Literal` choices or a `choices` hint, and a Map a
  `dict[str, str]` field.
- A Map takes no `value` (use `default_factory=dict` or `= {}`);
  `entries=[{"key": ..., "label": ..., "type": "Text", "value": ...}]` fixes
  its keys, labels, and defaults. Hinted keys must fit `Literal`/`Enum` keys
  and key patterns; entries are checked against the schema's entry rules.
- Map `constraints` apply to every value: value `min_length ≥ 1` →
  `notEmpty`, plus value `min_length`/`max_length`/`pattern`; a key pattern →
  `keyPattern`. Required does not add `notEmpty`; set
  `"constraints": {"notEmpty": true}` per entry instead.
- `Literal` map values turn entries into Dropdowns and need fixed keys;
  hinted `choices` must be among them, and a Dropdown entry's `value` must
  be one of its choices. Map keys must be strings.
- `group` hints move one input into another of the spec's `groups`.
- `constraints.notEmpty` (non-Map): `minLength ≥ 1`, `minItems ≥ 1`, or a
  required `String` property.
- `binding`: `{"type": "camunda:inputParameter", "name": alias}`.
- Presentation hints: `value=None` (pre-fill nothing), `placeholder`
  (String/Text), `editable=False`, `choices=[{"name": ..., "value": ...}]`
  (labels for `Literal` values, or the choices of a `type="Dropdown"` `str`
  or a `list[str]`), `display="checklist"|"taglist"|None` (List with
  choices), `item_type="Date"` (List without choices), and
  `additional_entries=True` (user keys next to fixed Map `entries`).
- `optional=True` leaves an empty input out of the XML: String, Text, or
  Dropdown only, the field needs a contract default, and it cannot be
  `notEmpty`.
- `constraints={...}` is merged over the derived ones: `notEmpty`,
  `minLength`, `maxLength`, `pattern` (a string or `{"value", "message"}`),
  `minItems`/`maxItems` (List), `keyPattern` (Map). Contract patterns are not
  copied to scalar and list inputs, because the modeler value may be an
  expression such as `${id}`; write a modeler pattern that also accepts
  `\$\{.+\}`.
- `condition={"property": "<alias>", "equals": ...}` (or `oneOf`, `isActive`)
  shows the input only then; the referenced input gets `id: <alias>`. Hidden
  inputs are not written, so the field needs a default.
- `script_format="groovy"` with the script as `value` binds a script input.
- `TaskTemplate(additional_inputs=AdditionalInputs(label, description, group,
  mirror_outputs, constraints))` adds a Map bound to
  `camunda:additionalInputParameters` for inputs modeler users name
  themselves. The contract and `Validate Task Input` do not cover them; the
  task reads them as plain variables. `mirror_outputs=True` maps each back
  as `<name> = ${<name>}`.
- `TaskTemplate(groups=())` renders the properties ungrouped.
- `TaskTemplate(settings=(TaskSetting("asyncBefore", value=True), ...))`
  exposes engine settings as properties bound to `camunda:<name>`:
  `asyncBefore`, `asyncAfter`, `exclusive` (Boolean) and `jobPriority`,
  `taskPriority` (String, with optional `placeholder` and `constraints`).
  `hidden=True` fixes the `value`; `label`, `description`, and `group` are
  optional.
- `TaskTemplate(errors=(ErrorDefinition(id, expression, code, name,
  message=None), ...))` renders a `camunda:errorEventDefinition` property
  and a `bpmn:Error` scope. The engine evaluates `expression` on the
  worker's result (it can read the returned variables) and throws the BPMN
  error `code` instead of completing the task, so a successful Robot task
  can still raise a business error that a boundary event catches.

## Versioning a published task

- Compatible change (new input with a default, new output, labels,
  constraints): bump `version`, keep the topic and the Robot task.
- Breaking change (new required input, removed or renamed input or output,
  changed type): keep the old contract and task as `<Name>InputV<N>` and
  `<Task Name> V<N>`, change the current ones, move the spec to
  `topic="<topic>.v<N+1>"` with `version=N+1` and `keep_versions=(..., N)`,
  and keep the old topic in `[tool.purjo.topics]` pointing at the old task.
  The first version keeps its plain topic.
- `check` accepts a topic that only a kept version uses, and requires it to
  stay in `[tool.purjo.topics]` with `process-variables = false` and a
  defined task. Keep a test for the old task; `check` cannot compare it
  with the old contract.
- Retire a version only when no deployed definition or external task uses
  its topic: drop it from `keep_versions`, remove the topic, task, and
  contract, and regenerate.

## Output mapping

`String` property with `value: alias` and
`binding: {"type": "camunda:outputParameter", "source": "${alias}"}`; the
modeler user may rename the target process variable. Outputs accept only
`template_hints(value=..., group=..., optional=..., source=...,
script_format=..., condition=..., editable=...)`: `value="name"` changes the
default target, and `value=""` adds `optional: true` so no mapping is written
unless the modeler user names a variable. `optional=True` allows clearing a
pre-filled target, `source` maps from another expression than `${alias}`,
and `script_format` makes that source a script. Hinted names may not contain
whitespace, `$`, `{`, or `}`, and no two outputs may map to the same variable.

## Hints

Only the hints named above; unknown keys raise. Types, choices, defaults,
and `notEmpty` are derived, so prefer adjusting the model over adding hints.

## `check` enforces

- Committed JSON equals the rendered text (2-space JSON + newline); no stray
  `*.json` in `.operaton/element-templates/` (`generate` removes them).
- Spec topics equal `[tool.purjo.topics]`; none reserved; unique ids,
  filenames, and topics; `process-variables = false`.
- Suites are collected recursively, skipping hidden directories, `tests/`,
  `lib/`, `examples/`, and `test_*.robot`. Task, variable, and keyword names
  match the way Robot matches them (case, spaces, and underscores ignored;
  `${name: type}`, `scope=BPMN:TASK`, and `Library.Keyword` forms accepted).
  A task name defined in more than one suite is an error, since purjo would
  run all of them.
- Non-string inputs have typed suite defaults.
- The suite defining the topic's task declares every input alias, calls
  `Validate Task Input    <InputContract>` in that task, and sets every
  output alias with `VAR … scope=${BPMN:TASK}`.

## Schema

Pin the Operaton element-templates schema by version, e.g.
`https://gitlab.com/vasara-bpm/vscode-operaton-bpmn-js-modeler/-/jobs/artifacts/v0.8.3/raw/operaton-element-templates-schema-v0.8.3.json?job=release`
(the `?job=release` query is required). Use the same URL as `$schema` in the
templates; never commit a copy. Validation uses `jsonschema.Draft7Validator`.
